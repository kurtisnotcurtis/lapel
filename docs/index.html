1 Cross-boundary reachability

lapel provider reachability

Your inference server lives on Windows while your CLI agent runs in Linux. lapel resolves the real NAT gateway from /proc/net/route and probes the endpoint from inside WSL2, where reachability actually breaks.

WSL2 Agent /proc/net/route → 172.x.x.1:1234 Host GPU Server
REACHABLE BIND_LOCALHOST FIREWALL_TIMEOUT LM Studio + Ollama
  • Avoids flaky DNS: skips unreliable /etc/resolv.conf nameserver guesses and reads kernel routes directly.
  • Actionable diagnostics: separates bind-address misconfigurations from Windows Firewall drops.

2Lean WSL2 distro (lapel)

lapel provision

Provisions a purpose-built Ubuntu 24.04 rootfs under %LOCALAPPDATA%\lapel\distros\lapel with pre-pinned dev runtimes and none of stock WSL’s desktop overhead.

uv · Python 3.12 fnm · Node LTS golang-go ripgrep · jq · yq git · tmux · sshd

  • Idempotent updates: queries dpkg-query first and skips redundant apt-get work on re-runs.
  • Resource auditing: pairs with lapel config to verify .wslconfig RAM, vCPU, and swap caps.

3 Sandboxing & honest reporting

lapel jail-controls

Confines autonomous agent runs with non-root execution, clean PATH, workspace scoping, and verified process-group teardown, while reporting every control’s true enforcement level.

Linux-only PATH & non-root agent user ENFORCED
setsid process-group teardown & 300s timeout ENFORCED
Workspace scope (bind / rsync copy) REQUESTED
Host .wslconfig RAM & vCPU ceilings NEEDS-CONFIG
  • Zero orphan processes: guest-side setsid PGID teardown prevents runaway child shells after stop.
  • No security theater: never silently ignores a policy or claims enforcement the host does not provide.

The user journey

Start interactively with three commands, or manage reproducible team environments declaratively via lapel.yaml.

lapel doctor

Verify WSL2 availability, GPU/VRAM specs, model tier recommendations, and provider reachability.

lapel setup

Guided setup to verify providers, provision the lapel WSL distro, mount your workspace, and configure jail policies.

lapel run

Launch your coding agent (pi, claude-code, copilot) inside the sandboxed WSL environment.

init / plan / apply

Declarative lapel.yaml lifecycle backed by SQLite drift detection (.lapel/state.db).

Supported providers & agents

Bring your own inference server and your own coding agent; lapel wires them together cleanly.

Declarative configuration (lapel.yaml)

Scaffold a reproducible project manifest with lapel init and apply it with lapel apply.

apiVersion: lapel.dev/v1
name: my-project

environment:
  distribution: lapel
  base: ubuntu
  version: "24.04"
  packages:
    - fd-find
    - tree
  style:
    preset: lapel-dark   # "lapel-dark" | "amber" | "minimal" | "none"
    windowsTerminal: true

provider:
  name: local
  type: lm-studio
  baseURL: "http://127.0.0.1:1234"
  connectionTimeout: 8s

agent:
  name: pi
  provider: local

workspace:
  name: my-project
  path: "."
  importMode: bind   # "bind" for live bind mounts or "copy" for isolated rsync copies

jail:
  name: developer
  profile: developer
  user: agent
  filesystem:
    "C:\\Users\\user\\Projects": read-write
    "C:\\Windows\\System32": deny
  network: unrestricted
  processes:
    privileged: false
    timeoutSeconds: 300

Local-first privacy

Hardware detection and baseline model recommendations run 100% locally during lapel doctor and lapel setup. Optional community benchmark sharing (lapel community) is strictly opt-in via LAPEL_COMMUNITY_ENABLED=true, and can be pointed at a self-hosted backend via LAPEL_COMMUNITY_ENDPOINT.
